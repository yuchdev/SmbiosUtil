# 03 - Examples and documentation

**Parent story:** [README.md](README.md)
**Status:** ✅ Complete (2026-11-10)
**Depends on:** Task 01 (YAML renderer) and Task 02 (CSV example, `--format` CLI wiring)
**Requirement:** R7 ([plan.md](../plan.md))

## Objective

Make milestone 0009 usable by someone who did not write it. This task adds:

- runnable, self-contained example programs that are built by default and
  run in CTest, so they cannot rot;
- a deterministic sample fixture, so every output sample shown in the docs
  is generated by the real code, not written by hand;
- a user guide, a developer guide, Doxygen completeness on the new public
  headers, and updates to the existing docs.

## Decisions recorded by this spec

### D1 - Examples location: a new top-level `examples/`, CSV stays in `smbios/examples/`

| Program | Location | Why |
|---------|----------|-----|
| (a) `format_table` | `examples/format_table/main.cpp` | A standalone *library consumer*. It links `libsmbios`, not the CLI. |
| (b) `read_fields` | `examples/read_fields/main.cpp` | Same as (a). |
| (c) CSV formatter | `smbios/examples/csv_formatter.cpp` (unchanged, Task 02) | Compiled *into the `smbios` executable*. Moving it would reopen ratified Task 02 and the R5 wording. |
| (d) JSON smoke helper | `examples/scripts/check_structured_output.py` | Used by CTest only. Documented as a snippet. |

Why the split, rather than putting (a) and (b) under `smbios/examples/`:

- `smbios/` is the CLI target's directory. Anything placed there reads as
  "part of the CLI".
- The repository convention is one top-level directory per build product
  (CLAUDE.md, Architecture). (a) and (b) are separate executables with their
  own link line.
- The two directories have different link shapes, and the docs explain the
  difference as a teaching point:
  - `examples/` links `libsmbios` like an external consumer would, so it
    needs whole-archive linking.
  - `smbios/examples/` adds an object directly into an existing executable,
    so it needs no whole-archive flag.
- `examples/README.md` points to `smbios/examples/csv_formatter.cpp`, so a
  reader finds all three examples from one place.

### D2 - Deterministic input: generated sample fixture; examples run live and must degrade

What exists today:

- The CLI's `--read-file` is parsed and then ignored. It is a `TODO` in
  `smbios/src/main.cpp`, and Task 02 keeps it out of scope.
- [docs/security/README.md](../../../security/README.md) requires a
  `--dump-file`/`--read-file` trust model *before* `--read-file` is
  implemented.
- `--dump-file` writes only the raw structure table. It does not record the
  SMBIOS version, so a dump cannot be re-decoded with correct version gating
  anyway.
- `SMBios` has no public constructor that takes a buffer or a source. Only
  the test-only `SmbiosTableWalkTestAccess` friend seam
  (`tests/unit/synthetic_table_builder.hpp`) can inject bytes, and examples
  must not teach users to rely on a test seam.

Therefore:

1. **Examples (a) and (b) read the live machine** through `SMBios bios;`
   and are written to **degrade, not fail**. If no source yields a table
   (Linux CI runs unprivileged and `/sys/firmware/dmi/tables/DMI` is
   root-only; some Windows runners expose no usable table), they:
   - print one notice to `stderr`;
   - still emit a well-formed, empty document (for example `[]` for JSON);
   - exit 0.

   Their CTest checks therefore assert *exit status and well-formedness*,
   never content. That result is the same on every OS and every privilege
   level.
2. **Doc samples come from a code-built fixture**, not from a binary dump
   and not from an example run. See D3.
3. A public injectable-source constructor plus a real `--read-file` (which
   would let the examples take a fixture path) is a cross-component
   contract change that needs an ADR and the security trust model. It is
   **out of scope** and recorded as an open question in `status.md`.

### D3 - Fixture: built in code by `SyntheticTableBuilder`; no binary file is checked in

- **Generator:** `tests/unit/doc_sample_fixture.hpp`/`.cpp` (new) provides
  ```cpp
  namespace smbios::test {
  /// @brief Builds the fixed, synthetic SMBIOS table used to generate every
  /// output sample in docs/output-formats.md. Deterministic: same bytes on
  /// every OS, every run. Contains no real hardware identifiers.
  std::vector<uint8_t> build_doc_sample_table();
  /// @brief SMBIOS version the sample table is decoded against (3.4).
  SMBiosVersion doc_sample_version();
  }
  ```
  It is built with `SyntheticTableBuilder::add_structure()` and fed through
  `SmbiosTableWalkTestAccess::parse_synthetic_table()`.
- **Contents** (kept small so each sample can be embedded in full). Together
  the three structures cover all four `FieldValue` alternatives and one
  visible case of each escaping rule:

  | Type | Structure | Demonstrates |
  |------|-----------|--------------|
  | 0 | BIOS Information | `std::string`; `bool` (exactly two characteristic bits set, so set-bits-only is visible); vendor `Example "Firmware" & Co.` (XML `&amp;`/`&quot;`, JSON `\"`, YAML `\"`, CSV `""` doubling) |
  | 11 | OEM Strings | `uint64_t` (`"String Count"`); one string `=EXAMPLE()` (CSV formula-injection `'` prefix) |
  | 32 | System Boot Information | `std::vector<uint8_t>` (`"Status Data"` with a non-empty fixed payload, as lowercase hex) |

- **Privacy constraint (hard rule).** Firmware dumps carry serial numbers,
  UUIDs and asset tags. The fixture contains **no** System Information
  (type 1), Baseboard (type 2), Chassis (type 3) or Memory Device (type 17)
  structure. Every string is an obviously synthetic `Example ...` literal. No
  byte sequence is copied from a real machine or a VM dump. If a later
  change adds a type that carries an identifier, the identifier must be a
  literal such as `EXAMPLE-SERIAL-0000`, and the UUID must be the fixed
  pattern `00112233-4455-6677-8899-aabbccddeeff`. A reviewer rejects any
  fixture byte that cannot be traced to a literal in
  `doc_sample_fixture.cpp`.
- **Golden outputs:** `tests/data/output_formats/sample.{txt,xml,json,yaml,csv}`
  (new directory). They are produced by rendering the fixture through
  `get_output_formatter(name)` with exactly the CLI's framing loop:
  `begin_document()`, then each `render(entry)` with `entry_separator()`
  between entries, then `end_document()`. The `text` sample has no CLI
  preamble. `docs/output-formats.md` says so and links to
  [cli-usage.md](../../../cli-usage.md) for the preamble.
- **Line endings:** add `/.gitattributes` with
  `tests/data/output_formats/** -text`, so Windows checkouts compare
  byte-for-byte.

- **Create** `examples/CMakeLists.txt`, `examples/README.md`,
  `examples/format_table/main.cpp`, `examples/read_fields/main.cpp`,

- **Modify** root `CMakeLists.txt`:
  - Add `option("SMBIOS_BUILD_EXAMPLES" SMBIOS_BUILD_EXAMPLES ON)`. The
    default is **ON**, so CI always builds the examples. This is unlike
    `SMBIOS_BUILD_FUZZERS`.
  - Add `if(SMBIOS_BUILD_EXAMPLES) add_subdirectory(examples) endif()` after
    `add_subdirectory(smbios)`.
- **Linking, "as a consumer would"** (`examples/CMakeLists.txt`):
  - Use `target_link_libraries(<ex> PRIVATE libsmbios)` and the include
    path `${CMAKE_SOURCE_DIR}/libsmbios/include`.
  - Add the **same three-way whole-archive block** used in
    `smbios/src/CMakeLists.txt` (`-force_load` / `/WHOLEARCHIVE` /
    `--whole-archive`). Give it a comment explaining that without the block,
    `get_output_formatter("json")` returns `nullptr` and
    `SMBiosEntryFactory::create()` returns `nullptr` for every type.
  - The duplication is deliberate and teaches the pitfall. Factoring a
    `smbios_link_whole_archive()` CMake helper for all four call sites is a
    separate follow-up, not this task. CMake 3.24's
    `$<LINK_LIBRARY:WHOLE_ARCHIVE,...>` is not available at the root
    `cmake_minimum_required(VERSION 3.13)`.
  - Apply `${SMBIOS_COMPILE_OPTIONS}`, `${SMBIOS_WARNING_OPTIONS}` and
    `${SMBIOS_LINK_OPTIONS}`, as `smbios/src/CMakeLists.txt` does.
  - Set `FOLDER "Examples"`.
- **(a) `examples/format_table/main.cpp`.** Target `smbios_example_format_table`.
  About 40 lines of code, heavily commented.
  - Usage: `smbios_example_format_table <format-name>`.
  - Steps, each with a comment saying *why*:
    1. Resolve `get_output_formatter(argv[1])` **before** constructing
       `SMBios`, the same fail-fast rule as R6. On `nullptr`, print
       `Unknown output format '<name>'. Registered formats: <comma-joined
       registered_output_formatter_names()>` to `stderr` and exit 2.
    2. Construct `SMBios bios;`. If `get_structures_count() == 0`, print one
       notice to `stderr` (D2).
    3. Write `begin_document()`. For each `DMIHeader`, call
       `SMBiosEntryFactory::create(header, version, table_end)`, skip
       `nullptr`, and write `entry_separator()` before every non-first
       rendered entry and then `render(*entry)`. Finally write
       `end_document()`.
  - Exit 0.
  - A comment states that `csv` is **not** available here: it is linked
    into the `smbios` CLI only. Which formats exist depends on which objects
    are linked into *this* binary.
- **(b) `examples/read_fields/main.cpp`.** Target `smbios_example_read_fields`.
  No formatter. It shows the data-model API directly:
  - Walk entries; switch on `header.type` with `SMBios::BIOSInformation` and
    `SMBios::MemoryDevice`.
  - `std::visit` with an `overloaded{...}` lambda set over all four
    `FieldValue` alternatives (string / `uint64_t` / `bool` / bytes). There
    must be no `std::get` that can throw.
  - Print BIOS `Vendor`, `Version` and `Release Date`. Print the count of
    `bool` fields, which is the number of set BIOS characteristics (bitmask
    semantics). For each Memory Device, print `Device locator`,
    `Device size` and `Device type`.
  - A comment states the **text-parity** reality: `Device size` is a
    `std::string` such as `"8192 MB"`, not a `uint64_t`, because R1 builds
    fields from the existing text getters. The example shows how to tell
    alternatives apart, and does not parse the string.
  - **Privacy:** the example deliberately does **not** print
    `Serial Number`, `Asset Tag`, `Part Number` or `UUID`. A comment explains
    that these are potentially identifying and that the program's output
    lands in CI logs.
  - If the table is empty, print the D2 notice and exit 0.
- **(d) `examples/scripts/check_structured_output.py`.** A standard-library
  script. Run it as `python3 -I check_structured_output.py --format json|xml -- <command> [args...]`.
  - It runs the command as a subprocess and requires exit 0.
  - It parses stdout with `json.loads` or `xml.etree.ElementTree.fromstring`.
  - JSON must be a list of objects, each with a `"type"` string and a
    `"fields"` object. XML must have one root element.
  - **It prints only** `ok: <format>, <N> structures`. It never echoes any
    parsed value or the raw stdout, including on failure, where it prints
    only the error position. This keeps CI logs free of the runner's
    serials and UUIDs.
- **`examples/cmake/run_quiet.cmake`.** Runs `${CMD}` via `execute_process`
  with stdout discarded and stderr kept. It fails if the exit code differs
  from `${EXPECT}` (default 0). The same no-values-in-logs rationale
  applies.
- **CTest registrations**, all in `examples/CMakeLists.txt`, named
  `smbios_example_*`:

  | Test | Command | Gate |
  |------|---------|------|
  | `smbios_example_format_table_<fmt>` for `text`, `xml`, `json`, `yaml` | `run_quiet.cmake` around `format_table <fmt>` | exit 0 |
  | `smbios_example_format_table_unknown_format` | `run_quiet.cmake` with `EXPECT=2`, `format_table bogus` | exit 2 |
  | `smbios_example_read_fields` | `run_quiet.cmake` around `read_fields` | exit 0 |
  | `smbios_example_format_table_json_parses` | `check_structured_output.py --format json -- format_table json` | Python3 only |
  | `smbios_example_format_table_xml_parses` | `check_structured_output.py --format xml -- format_table xml` | Python3 only |
  | `smbios_example_cli_json_parses` | `check_structured_output.py --format json -- $<TARGET_FILE:smbios> --format json` | Python3 only |

  - Guard the Python rows with
    `find_package(Python3 COMPONENTS Interpreter)` and
    `if(Python3_Interpreter_FOUND)`, and invoke `${Python3_EXECUTABLE} -I`.
  - If Python is missing, emit a `message(STATUS ...)`. Configuration must
    not fail.
  - Use `$<TARGET_FILE:...>` everywhere. No hard-coded output directory.
  - Set a CTest `TIMEOUT` of 60 on each test, matching CI's `--timeout 60`.
- **Modify** `.github/workflows/ci.yml`. Extend **both** "must pass" ctest
  regexes (the `build` job and the `sanitizers` job), which today are
  `smbios_unit_test|smbios_mock_test|smbios_c_`, with `|smbios_example_`.
  Without this the example tests are built but never run in CI. The
  examples are designed to degrade (D2), so they belong in the must-pass
  set, not in the warning-only integration step.

### New documentation (`docs-writer`)

#### `docs/output-formats.md` (user guide)

Outline:

1. **Choosing a format.** `smbios --format <name>` / `-f`. Covers:
   - the default, `text`, which is byte-identical to the pre-0009 output;
   - the list `text`, `xml`, `json`, `yaml`, `csv`;
   - `--help`, which shows the registered list;
   - the unknown-name error and its non-zero exit;
   - the fact that `--dump-file` ignores `--format`.
2. **Document shape per format.** One subsection each for text, xml, json,
   yaml and csv. Each has two to four sentences on the shape (root
   element / array / sequence / header row) and the **full** golden sample,
   embedded under a `<!-- sample: ... -->` marker (D3).
3. **Type mapping.** One table: rows are the `FieldValue` alternatives
   (`std::string`, `uint64_t`, `bool`, `std::vector<uint8_t>`), columns are
   the formats. Bytes always become lowercase hex without separators.
4. **Escaping and sanitisation guarantees.**
   - Invalid UTF-8 becomes U+FFFD in every structured format.
   - XML replaces forbidden control characters with U+FFFD instead of
     escaping them, and emits no DOCTYPE.
   - JSON uses `\uXXXX` and short-form escapes, and escapes U+2028/U+2029.
     Integers are exact decimal digits; consumers that use IEEE doubles
     (JavaScript `JSON.parse`) lose precision above 2^53. Python `json`, Go
     `json.Number` and jq 1.7+ read them exactly.
   - YAML double-quotes every string, with the implicit-typing trap examples
     (`NO`, `1.10`, `0x0A`, `~`), and emits no anchors, aliases or tags.
   - CSV uses RFC 4180 quoting, plus the `'` prefix for a leading `=` `+`
     `-` `@` TAB or CR (CWE-1236). Values that begin with `-` show the
     prefix too, and this trade-off is accepted.
   - `text` is **not** sanitised (known gap; post-0009 follow-up). Do not
     pipe untrusted `text` output to a terminal that interprets escape
     sequences.
5. **Bitmask fields.** Only *set* bits appear, one `name: true` field each.
   An absent name means the bit is clear or the field is not applicable;
   it does not mean `false`.
6. **What the fields contain (text parity).** Fields mirror
   `render_to_description()`. Many numeric quantities are strings (for
   example `"8192 MB"`), and there is no full decode. The guide links to
   the known mirrored quirks listed in this milestone's
   [status.md](../status.md) Notes & decisions. Field names are
   stable library constants, unique per entry, and repeated groups get
   1-based suffixes.
7. **Stability.** There is no formal schema or DTD in v1 (plan non-goals).
   The shape is "one element/object per entry, one field per `NamedField`".
   Field names and value types may change in a future milestone, and such a
   change is called out in the roadmap.
8. **Consuming JSON from scripts.** This is example (d), as snippets:
   - `smbios --format json | jq -r '.[] | select(.type=="BIOS Information") | .fields.Vendor'`
   - `smbios --format json | python3 -c "import json,sys; ..."`

   State that `examples/scripts/check_structured_output.py` is the
   CTest-checked version.
9. **Privacy note.** Output contains serial numbers, UUIDs and asset tags.
   Redact before sharing it, for example in a bug report. The library never
   logs field values.

Acceptance:

- Every sample block has a `<!-- sample: -->` marker, and
  `scripts/check_doc_samples.py --check` passes.
- No hand-written output appears, except shape-only illustrations, which
  must be labelled "illustrative" and use `...`.
- The escaping section names every rule in
  [Story 02.0 Task 02](../02.0-renderer-registry-and-built-in-formats/02-text-xml-and-json-renderers.md)
  and [Task 01](01-yaml-renderer.md), and nothing beyond them.
- `feature-reviewer` confirms every claim against the code.

#### `docs/dev/custom-output-formatter.md` (developer guide)

Outline:

1. **When to write a formatter, and when to consume `get_fields()`
   directly** (point to example (b)).
2. **Walkthrough: the CSV formatter, step by step.** Quote excerpts from
   `smbios/examples/csv_formatter.cpp` by line range, not by copying it in
   full:
   1. include only `<libsmbios/output_formatter.hpp>`,
      `<libsmbios/abstract_smbios_entry.hpp>` and
      `<libsmbios/formatters/formatter_escaping.hpp>`, and never
      `tables/*.hpp`;
   2. subclass `IOutputFormatter`, implementing `format_name()` and
      `render()`;
   3. optionally implement `begin_document()`/`entry_separator()`/`end_document()`
      (CSV writes its header row here);
   4. `std::visit` over `FieldValue`;
   5. reuse the escaping helpers and `hex_encode()`, and never hand-roll a
      UTF-8 decoder;
   6. invoke `REGISTER_OUTPUT_FORMATTER(CsvFormatter)` in the `.cpp` only.
3. **Registration and linking pitfalls.**
   - Static-init registration runs only for linked object files.
   - Whole-archive linking of `libsmbios` applies in `smbios`, `smbios_c`,
     `tests/c_abi` and `examples/`.
   - Compiling the formatter directly into the executable (the
     `smbios/examples/CMakeLists.txt` pattern) needs no flag.
   - `smbios_unit_test` does not force-load, so define members out of line
     and name the class in the test.
   - A duplicate `format_name()` throws `std::logic_error` at static init.
   - The header-registration double-count trap is the same as for
     `REGISTER_SMBIOS_ENTRY`.
4. **Rules a formatter must keep.**
   - Render exactly what `get_fields()` returns, with no clamping or
     synthesising.
   - Field names are values, never element or attribute names (CWE-91).
   - Never log field values.
   - Output is deterministic, with no timestamps or host data.
5. **Testing a formatter.**
   - Use `FieldsTestEntry` from Story 02.0 Task 03 for exact values.
   - Use `SyntheticTableBuilder` for real entries.
   - Use the structural validators (`is_well_formed_json`/`_xml`).
   - Cover the hostile-string cases from Story 02.0 Task 03.
   - Add a golden sample to `doc_samples_test.cpp` if the format is
     built in.
6. **Regenerating doc samples** (the two-command flow above).

Acceptance:

- Following the guide verbatim, a reader can add a sixth format in a new
  `.cpp` without editing any existing `libsmbios` source. `feature-reviewer`
  dry-runs this by reading.
- Every pitfall names the `CMakeLists.txt` that demonstrates it.

## Functions and Classes

- `smbios::test::build_doc_sample_table()` and `doc_sample_version()` - new,
  test support only.
- Two example `main()` functions - new, outside every library.
- There are no new or changed library symbols. Only Doxygen comments are
  added.

## Constraints

- No library source change. Examples use only the public headers
  `<libsmbios/smbios.hpp>`, `<libsmbios/smbios_entry_factory.hpp>`,
  `<libsmbios/output_formatter.hpp>` and `<libsmbios/field_value.hpp>`.
  (b) may additionally include `<libsmbios/abstract_smbios_entry.hpp>`.
  Neither includes `tables/*.hpp` or any `tests/` header.
- No new dependency. Python is optional for CTest and never required to
  build.
- **Privacy (hard):**
  - The fixture contains no real identifiers (D3).
  - CTest commands and `check_structured_output.py` never echo field
    values (D1(d)).
  - (b) never prints identifying fields.
  - The docs show only fixture-generated samples.
- C++20, the project warning flags, and `cpp_coding_standard.md`. Examples
  carry a file-level Doxygen `@file` comment.
