## Story 04.0 - Sensors, Probes, and Small System-Control Structures (✅ 2026-11-09)

**Task 01 delivered:** `PointingDeviceEntry` (`SMBios::PointingDevice` = 21, DSP0134 3.9.0 7.22, Table 87) - Device Type (7.22.1, Table 88) and Interface (7.22.2, Table 89) enums plus Number of Buttons, with the accessor deliberately named `get_device_type()` (never `get_type()`) to avoid shadowing the inherited structure-kind accessor. `PortableBatteryEntry` (`SMBios::PortableBattery` = 22, 7.23, Table 90) - Location/Manufacturer/Device Name/SBDS Version strings, Manufacture Date and Serial Number strings each with a `uses_sbds_manufacture_date()`/`uses_sbds_serial_number()` predicate for the "index 0 means see SBDS instead" 2.2+ convention (SBDS data itself not decoded), Device Chemistry enum (7.23.1, Table 91), Design Capacity (mWh) and Design Voltage (mV) each with a known/unknown predicate, and Maximum Error percentage.

**Design Capacity Multiplier resolution (the task's own flagged open question):** read directly from `docs/standard/DSP0134_3.9.0.md`'s full Table 90, the Design Capacity Multiplier IS a separate structure field - offset 0x15h, BYTE, 2.2+, immediately after SBDS Device Chemistry (0x14h) and before the OEM-specific DWORD (0x16h) - not merely prose about external interpretation. `PortableBatteryEntry::get_design_capacity()` therefore returns the EFFECTIVE value: the raw 0x0A WORD multiplied by the 0x15 BYTE when that field is present (`get_entry_size() >= 0x16`), defaulting the multiplier to 1 (the spec's own documented default) both when the field is absent on a shorter/pre-2.2 structure and defensively if present-but-zero. The 0x0A field's own "0 means unknown" sentinel is checked pre-multiplication. The raw multiplier byte itself is not exposed as a separate public accessor, since the task's accessor list calls only for the already-resolved effective capacity; it is used internally via a private helper.

**Location-and-Status cross-check (the task's own flagged open question):** read directly, per-subsection, from `docs/standard/DSP0134_3.9.0.md`. The Status sub-field (bits 7:5) is confirmed BYTE-IDENTICAL across all four subsections (7.27.1/7.28.1/7.29.1/7.30.1 all enumerate the same six values - Other/Unknown/OK/Non-critical/Critical/Non-recoverable - at the same bit positions), so each class carries the identical nested `Status` enum/string table (duplicated per class to match this codebase's existing per-class nested-enum convention, e.g. `SystemResetEntry::BootOption`, rather than introducing a new shared cross-class enum type). The Location/Device-Type sub-field (bits 4:0) is NOT identical across all four: VoltageProbeEntry's and ElectricalCurrentProbeEntry's own Location (Table 96/Table 102) are byte-identical 11-value lists (Other..Add-in Card), but TemperatureProbeEntry's own Location (Table 100) is a 15-value SUPERSET adding Front Panel Board/Back Panel Board/Power System Board/Drive Back Plane; CoolingDeviceEntry's Device Type (Table 98) is an unrelated enumeration (fans/blowers/heat pipes/refrigeration/active-passive cooling). Each class therefore owns its own Location/DeviceType enum, per the task's own explicit instruction not to assume a shared decode table without confirming.

**Discrepancy found against this milestone's own roadmap task document:** that document's field list for Voltage Probe and Temperature Probe stops at 0x10 OEM-defined and attributes the 0x14 Nominal Value WORD field only to Electrical Current Probe (29). Table 95 and Table 99 as they actually read in `docs/standard/DSP0134_3.9.0.md` show the IDENTICAL 0x14 Nominal Value field (same `0x8000`-unknown sentinel, same length-gating idiom) present for Voltage Probe (mV) and Temperature Probe (1/10 degree C) too, not just Electrical Current Probe (mA). All three probe classes therefore implement `get_nominal_value()`/`is_nominal_value_known()`/`has_nominal_value()`, each documented with the discrepancy note in its own header.

**Off-by-one safety deviation from literal spec text:** DSP0134 3.9.0's own prose gates CoolingDeviceEntry's Nominal Speed on "length larger than 0Ch" (i.e. length >= 0x0D) and each probe's Nominal Value on "length larger than 14h" (i.e. length >= 0x15) - but both are 2-byte WORD fields, so a length of exactly one more than the base minimum can only supply the field's low byte. `has_nominal_speed()`/`has_nominal_value()` therefore require the FULL field (length >= 0x0E / >= 0x16 respectively) before reporting it present, treating the single-byte-short length defensively as "not yet present" rather than reading one byte of the adjacent string section as the field's high byte - documented explicitly in each accessor's own doc comment. CoolingDeviceEntry's Description gate (single-byte STRING index, "0Fh or larger") has no such concern and uses the literal `length >= 0x0F` guard.

**Shared sentinel-check helper:** each `.cpp` defines its own anonymous-namespace `is_word_value_unknown(uint16_t)` helper (one per file, used at every one of that class's WORD-field call sites), per this story's own Key constraints note ("implement once per .cpp").
