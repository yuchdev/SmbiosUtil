# Output Formats

`smbios` can print the SMBIOS table as plain text, XML, JSON, YAML or CSV. This guide covers choosing
a format, the shape of each document, and the escaping guarantees you can rely on. To add a format of
your own, see [the custom formatter guide](dev/custom-output-formatter.md).

Every sample below is generated by the real code from a synthetic fixture (three invented
structures), never from a real machine, and is kept byte-identical to the golden files in
`tests/data/output_formats/` by `scripts/check_doc_samples.py`.

## Choosing a format

```bash
smbios --format json        # or -f json
smbios -f yaml
```

- The default is `text`. Its output is byte-identical to the output before structured formats
  existed, including the `DMI version` / `Table size` preamble described in
  [cli-usage.md](cli-usage.md).
- The built-in formats are `text`, `xml`, `json` and `yaml`. `csv` is an example formatter compiled
  into the `smbios` executable (see [Custom formatter guide](dev/custom-output-formatter.md)).
- `smbios --help` lists the formats registered in your build.
- An unknown name prints `Unknown output format '<name>'. Registered formats: ...` to stderr and
  exits with status 1. The name is validated before the SMBIOS table is read.
- `--dump-file` ignores `--format`: it still prints the legacy text and writes the raw table.
- Structured formats print only the document: no `DMI version`/`Table size` preamble.

## Document shape per format

### text

The legacy human-readable description of each structure. The sample is the formatter's per-entry
output only; the CLI adds its preamble and `Header ID = N` lines (see [cli-usage.md](cli-usage.md)).

<!-- sample: tests/data/output_formats/sample.txt -->
```text
Header type: BIOS Information
Vendor: Example "Firmware" & Co.
Version: Example 1.0
Address: 0xf000
Runtime size: 64 kB
Release Date: Example 01/01/2026
ROM Size: 128 kB
BIOS properties: 
	PCI is supported
	BIOS is upgradeable
BIOS properties extend1: 
BIOS properties extend2: 
BIOS Revision: 1.0
Firmware Revision: 2.0
Header type: OEM Strings
String Count: 1
String 1: =EXAMPLE()
Header type: System Boot Information
Status: No errors detected
Status Data: 01 23 ab cd
```

### xml

One `<smbios>` root element, one `<structure type="...">` per entry and one
`<field name="...">` per field. Names and types are attribute values, never element names. The
value's original type is not recorded in the markup.

<!-- sample: tests/data/output_formats/sample.xml -->
```xml
<?xml version="1.0" encoding="UTF-8"?>
<smbios>
  <structure type="BIOS Information">
    <field name="Vendor">Example &quot;Firmware&quot; &amp; Co.</field>
    <field name="Version">Example 1.0</field>
    <field name="Address">0xf000</field>
    <field name="Runtime size">64 kB</field>
    <field name="Release Date">Example 01/01/2026</field>
    <field name="ROM Size">128 kB</field>
    <field name="PCI is supported">true</field>
    <field name="BIOS is upgradeable">true</field>
    <field name="BIOS Revision">1.0</field>
    <field name="Firmware Revision">2.0</field>
  </structure>
  <structure type="OEM Strings">
    <field name="String Count">1</field>
    <field name="String 1">=EXAMPLE()</field>
  </structure>
  <structure type="System Boot Information">
    <field name="Status">No errors detected</field>
    <field name="Status Data">0123abcd</field>
  </structure>
</smbios>
```

### json

One array with one object per entry: `"type"` (string) and `"fields"` (object). Numbers and booleans
keep their JSON types.

<!-- sample: tests/data/output_formats/sample.json -->
```json
[
  {
    "type": "BIOS Information",
    "fields": {
      "Vendor": "Example \"Firmware\" & Co.",
      "Version": "Example 1.0",
      "Address": "0xf000",
      "Runtime size": "64 kB",
      "Release Date": "Example 01/01/2026",
      "ROM Size": "128 kB",
      "PCI is supported": true,
      "BIOS is upgradeable": true,
      "BIOS Revision": "1.0",
      "Firmware Revision": "2.0"
    }
  },
  {
    "type": "OEM Strings",
    "fields": {
      "String Count": 1,
      "String 1": "=EXAMPLE()"
    }
  },
  {
    "type": "System Boot Information",
    "fields": {
      "Status": "No errors detected",
      "Status Data": "0123abcd"
    }
  }
]
```

### yaml

One explicit YAML 1.2 document holding a block sequence with one mapping per entry (`type`,
`fields`). An entry with no fields renders `fields: {}`. A document with zero entries is `---`
followed by an empty line, which a parser loads as null (Python `yaml.safe_load` returns `None`),
not as an empty list: treat null as "no entries".

<!-- sample: tests/data/output_formats/sample.yaml -->
```yaml
---
- type: "BIOS Information"
  fields:
    "Vendor": "Example \"Firmware\" & Co."
    "Version": "Example 1.0"
    "Address": "0xf000"
    "Runtime size": "64 kB"
    "Release Date": "Example 01/01/2026"
    "ROM Size": "128 kB"
    "PCI is supported": true
    "BIOS is upgradeable": true
    "BIOS Revision": "1.0"
    "Firmware Revision": "2.0"
- type: "OEM Strings"
  fields:
    "String Count": 1
    "String 1": "=EXAMPLE()"
- type: "System Boot Information"
  fields:
    "Status": "No errors detected"
    "Status Data": "0123abcd"
```

### csv

Available in the `smbios` CLI only. A header row `type,field_name,field_value`, then one row per
field in field order. An entry with no fields still yields one row (`<type>,,`) so it stays visible.
Rows end with LF, not RFC 4180's CRLF.

<!-- sample: tests/data/output_formats/sample.csv -->
```csv
type,field_name,field_value
BIOS Information,Vendor,"Example ""Firmware"" & Co."
BIOS Information,Version,Example 1.0
BIOS Information,Address,0xf000
BIOS Information,Runtime size,64 kB
BIOS Information,Release Date,Example 01/01/2026
BIOS Information,ROM Size,128 kB
BIOS Information,PCI is supported,true
BIOS Information,BIOS is upgradeable,true
BIOS Information,BIOS Revision,1.0
BIOS Information,Firmware Revision,2.0
OEM Strings,String Count,1
OEM Strings,String 1,'=EXAMPLE()
System Boot Information,Status,No errors detected
System Boot Information,Status Data,0123abcd
```

## Type mapping

Each field is one of four value types. Bytes always become lowercase hex without separators.

| Value type | text | xml | json | yaml | csv |
|------------|------|-----|------|------|-----|
| `std::string` | as printed | escaped text | string | double-quoted string | cell |
| `uint64_t` | as printed | exact digits | bare number | bare integer | exact digits |
| `bool` | (listed by name) | `true` / `false` | `true` / `false` | `true` / `false` | `true` / `false` |
| `std::vector<uint8_t>` | as printed | hex | hex string | hex string | hex |

Unsigned integers are written as exact decimal digits. JavaScript's `JSON.parse` reads numbers as
IEEE doubles and loses precision above 2^53; Python `json`, Go `json.Number` and jq 1.7+ read them
exactly.

## Escaping and sanitisation guarantees

Firmware strings are untrusted: any byte, not necessarily UTF-8. The structured formats guarantee
the following, and nothing beyond it. The threat model is
[2026-11-10-structured-field-model.md](security/2026-11-10-structured-field-model.md).

- **Invalid UTF-8 (xml, json, yaml, csv).** Strict UTF-8 validation. Each maximal invalid
  subsequence becomes one U+FFFD, so the output is always valid UTF-8.
- **XML.** Code points XML 1.0 forbids (most C0 controls, U+FFFE, U+FFFF) are replaced with U+FFFD,
  because they cannot even be written as character references. The five predefined entities are used
  for `& < > " '`. No character references, DOCTYPE or processing instructions are emitted (only the
  fixed XML declaration). A conforming parser normalises a raw CR to LF. XML guarantees
  well-formedness, **not** terminal safety: DEL and the C1 controls (including U+009B, the 8-bit CSI
  introducer) pass through raw. Prefer `json` for output shown in a terminal.
- **JSON.** `\"` and `\\`, short escapes (`\b \f \n \r \t`) and `\u00xx` for every other C0 control,
  plus DEL and the C1 controls (U+007F-U+009F) and U+2028/U+2029. Integers are exact (see above).
- **YAML.** Every string (keys, values, the `type` value) is double-quoted, so `NO`, `1.10`, `0x0A`
  and `~` always load as strings. Controls, DEL and C1 are escaped, U+0085/U+2028/U+2029 become
  `\N`/`\L`/`\P`, and U+FEFF is escaped. No anchors, aliases, tags or block scalars are emitted.
- **CSV.** RFC 4180 quoting (a cell with `"`, `,`, CR or LF is quoted, `"` doubled). A cell that
  begins with `=`, `+`, `-`, `@`, TAB or CR gets a leading `'` so spreadsheets do not evaluate it
  (CWE-1236). Values that begin with `-` therefore show the `'` too; this trade-off is accepted. The
  sample's `String 1` row shows the guard.
- **text is not sanitised.** It is byte-identical to the legacy output, so firmware text, including
  terminal escape sequences, reaches stdout unchanged (known gap, tracked as a post-0009 follow-up).
  Do not pipe untrusted `text` output to a terminal that interprets escape sequences.

Output is deterministic: no timestamps, host data or locale dependence, and `\n` line endings.

## Bitmask fields

Only bits that are *set* appear, one `name: true` field each (for example `PCI is supported` in the
samples). An absent name means the bit is clear or not applicable; it does not mean `false`.

## What the fields contain

Fields mirror the `text` output (a "text-parity" view). Many numeric quantities are decorated
strings such as `"8192 MB"` or `"0xf000"`, as in the samples above, and there is no full decode:
values that `text` never prints are not emitted. Some existing text-output quirks are mirrored
rather than fixed; they are listed in the milestone's
[status notes](roadmap/0009-structured-output-formats/status.md). Field names are stable library
constants, unique within an entry, and repeated groups carry a 1-based suffix (`String 1`).

## Stability

There is no formal schema or DTD in this release. The shape is one element/object per entry and one
field per name/value pair. Field names and value types may change in a future milestone; such a
change is called out in the roadmap.

## Consuming JSON from scripts

```bash
smbios --format json | jq -r '.[] | select(.type=="BIOS Information") | .fields.Vendor'

smbios --format json | python3 -c '
import json, sys
for entry in json.load(sys.stdin):
    if entry["type"] == "BIOS Information":
        print(entry["fields"].get("Vendor"))
'
```

`examples/scripts/check_structured_output.py` is the CTest-checked version of this idea; see
[examples/README.md](../examples/README.md).

## Privacy note

Real output contains serial numbers, UUIDs and asset tags. Redact it before sharing it, for example
in a bug report. The library never logs field values.
