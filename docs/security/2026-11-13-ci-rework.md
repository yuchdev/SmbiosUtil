## Assets & trust boundaries

- **Assets:**
  - Release artifacts and their integrity claim "tested equals shipped" (ADR 0005 DD1): the
    `install/<leg>/` tree, `dist/` archives, `manifest.json`, the GitHub Release, the registry PR,
    and the S3 staging copy.
  - Publish credentials: `GITHUB_TOKEN` with write scopes in publish jobs, the OIDC ID token and
    the assumed AWS role session, any `release`/`staging` environment secret.
  - The vcpkg binary cache (its archives are linked into the shipped binaries).
  - Firmware identifiers of the runner's (virtual) machine read by live-table steps.
  - Public CI logs, annotations, job summaries and artifacts (public repository).
  - The integrity of CI verdicts: a green check must mean the gates ran and passed (R-7/R-8,
    parity C01-C22).
- **Threat actors:**
  - A1: a fork-PR author (no write access; controls the PR's code, including workflow files run
    on `pull_request`).
  - A2: a collaborator or a stolen token with write or `workflows` scope (can push branches and
    tags, run `workflow_dispatch` on any branch, push directly to `master` because Q5 says there
    is no branch protection).
  - A3: a compromised upstream: a marketplace action tag, a PyPI wheel, the actionlint release, a
    vcpkg port source or build script, a runner-image tool.
  - A4: hostile data that is not PR-authored: a crafted SMBIOS table on the runner, tool output
    quoting third-party sources, REST/S3 responses.
- **Boundaries:**
  - **B1 - event -> workflow definition.** Which code and which YAML run, with which token
    permissions, environment and secrets. For `pull_request`, `push`, `workflow_dispatch` and tag
    pushes, the YAML is taken from the triggering ref, so every in-repo rule (policy gate P1-P13)
    is enforced by code the actor controls. Only repository settings (environment rules, rulesets,
    default token permissions) and the cloud-side OIDC trust policy sit outside that ref.
  - **B2 - child process -> step runner -> platform log.** Tool output becomes RC1 excerpts,
    annotations, `ok:`/`info:` lines, RC3 records and summaries. The platform interprets
    `::cmd::` (GitHub) or `##teamcity[...]` (TeamCity).
  - **B3 - child process -> platform side channels.** `GITHUB_ENV`, `GITHUB_OUTPUT`, `GITHUB_PATH`,
    `GITHUB_STEP_SUMMARY`, the OIDC request token, persisted git credentials, and the runtime token
    used by the cache and artifact services.
  - **B4 - run -> run** through the Actions cache (default-branch scope is readable by every
    branch and tag).
  - **B5 - job -> job in one run** through artifacts and job outputs (build -> package -> verify ->
    publish).
  - **B6 - publish job -> external stores** (GitHub Releases, registry repo, S3) under OIDC or
    token credentials.
  - **B7 - firmware -> live-table steps -> logs/JUnit/artifacts.**
  - **B8 - developer machine** (local `stage.py`/`ci_step.py` runs, `CI_REPORTER=plain`): temp
    files, logs holding live-table output.

## Findings

Severity is assessed for the pipeline as specified, assuming the per-task requirements below are
not applied. Story 01.0's code is already strong on its core job: commands run without a shell,
logs are streamed with bounded memory, excerpts are fenced with a per-fence 128-bit random token,
annotation text is escaped, and hostile-fixture tests exist for every backend. The findings below
are mostly about what surrounds that core.

### [HIGH] CR-1 In-repo policy is enforced by code the actor controls; staging tier, dispatch and tags reach credentials (CWE-284, CWE-863, CWE-269)
- Vector / evidence:
  - P8 (02.0 Task 03) allows `secrets.`/`id-token: write` only in a job with
    `environment: release`, `needs: verify` and a `v*` tag guard. ADR 0005 D9 adds `staging`-tier
    destinations (`environment: staging`, `permission_class: oidc`) that run on `master` pushes and
    `workflow_dispatch`. P8 as written forbids them, and P12 only fences the `release` tier. The
    two rules contradict each other, and nothing specifies the guard for the staging tier.
  - Any of `workflow_dispatch` on a feature branch, a push of a `v*` tag pointing at an unmerged
    commit, a direct push to `master` (Q5: no branch protection), or a `probe/**` branch runs the
    YAML **from that ref**. A2 can delete the tag guard, the `needs: verify` edge and the policy
    gate itself in the same commit. `ci.yml` ignores `probe/**` (04.0 Task 03), so a probe
    workflow is never policy-checked at all.
  - P8 bans only `pull_request_target`. `workflow_run`, `issue_comment`,
    `pull_request_review(_comment)` and `discussion*` triggers also run base-repo YAML with
    secrets on events A1 can cause, and `secrets: inherit` in a `workflow_call` forwards every
    secret to a stage workflow.
  - No spec names the repository settings that actually bound B1: default `GITHUB_TOKEN`
    permissions, environment deployment-branch/tag rules, required reviewers, tag rulesets, and
    fork-PR approval.
- Impact: an A2 actor, or a stolen PAT with `workflows` scope, obtains `contents: write` or an
  assumed AWS role, publishes an unverified release or staging object, or overwrites a release.
  A1 cannot do this today: `pull_request` from a fork gets a read-only token and no secrets.
- Mitigation:
  - **Repository side (the real boundary):**
    - Default workflow permissions: read-only. Disable "Allow GitHub Actions to create and approve
      pull requests" unless 0012's registry PR needs it, and record the decision.
    - Environment `release`: deployment rule "selected tags" `v*` only, required reviewer(s),
      "prevent self-review" on, no admin bypass.
    - Environment `staging`: deployment rule branch `master` only. Add a required reviewer if
      dispatch-triggered staging publishes are kept.
    - A tag ruleset: creating, updating or deleting `v*` tags is restricted to maintainers.
    - Fork-PR workflows require approval for outside contributors.
    - Record each setting with a `gh api` read-back in `docs/dev/ci.md`.
  - **Policy gate:**
    - [OVERRIDES SPEC] P8 bans every trigger except `push`, `pull_request`, `schedule`,
      `workflow_dispatch` and `workflow_call`, and bans `secrets: inherit`.
    - P8/P12 gain a staging clause: a job may reference `secrets.` or hold `id-token: write`
      only if it is listed in `publish_jobs.json` and uses `environment: release` (tag-guarded)
      or `environment: staging` (guarded to `refs/heads/master` push or dispatch, never
      `pull_request`), and `needs:` the same run's `verify` in both cases.
    - P12 also checks the caller job of every `uses: ./.github/workflows/stage-publish.yml`,
      because `workflow_call` caps permissions at the caller.
  - **Probe workflows:** the template sets `permissions: {}` plus `contents: read`, references no
    environment, and is safe only because of the read-only default and the environment rules
    above. State that dependency in the template header.
  - **In the publish stage** (0012): before any write, check that the tagged commit is an ancestor
    of `origin/master`. This is defence in depth; the environment reviewer is the control.
- Implemented by: 02.0 Task 03 (P8 [OVERRIDES SPEC], P12); 03.0 Task 04 cutover checklist (the
  settings, done by the maintainer); 04.0 Task 03 (probe template); 0012 Story 04.0.
- Verification: policy fixtures, each producing exactly its violation: `workflow_run` trigger,
  `secrets: inherit`, a staging job without `needs: verify`, a staging job reachable from
  `pull_request`, and a caller job widening permissions for `stage-publish.yml`. A recorded
  `gh api repos/{owner}/{repo}/environments` and `.../rulesets` read-back showing the rules. A
  dispatch of the publish stage from a non-`master` branch is rejected by GitHub with "branch not
  allowed to deploy to staging" (run ID recorded).

### [HIGH] CR-2 vcpkg binary-cache poisoning feeding release artifacts (CWE-345, CWE-494, CWE-829)
- Vector / evidence:
  - The 02.0 Task 02 key `vcpkg-<flavor>-<label>-<cxx>-<hash>-<run_id>` with a `restore-keys`
    prefix restores the **newest** matching entry. The `files` provider trusts an archive by its
    ABI-hash file name; the archive content is not authenticated.
  - Tag runs (D7: full matrix, then package -> publish) restore from the default-branch cache
    scope. Any code that executes in a `master`-scoped run can write a newer entry under the
    same prefix: a vcpkg port build script or downloaded source, a test, or a merged commit.
    With the runtime token taken from the runner process, that write can happen even from a job
    that never runs `actions/cache` save. This is the 2024 "Cacheract" class of attack. The
    poisoned Boost or other static library is then linked into the shipped `smbios_c` and CLI.
  - Positive: Task 02 already saves only on `master` pushes and `schedule`, and PR caches are
    scoped to the PR ref. A1 cannot reach the default-branch scope.
- Impact: attacker-chosen object code inside a signed-off release archive whose digest then
  verifies perfectly, because D4 digests are computed after the poisoned link.
- Mitigation:
  - [OVERRIDES SPEC] On `CI_EVENT=tag`, packaging legs build with
    `VCPKG_BINARY_SOURCES=clear` (cold build from the pinned baseline, whose port downloads are
    SHA-512-checked by vcpkg), restore no cache and save no cache. Staging-tier runs on `master`
    may use the cache. The manifest records `"binary_cache": "none"|"restored"` per leg, and
    `publish` to a `release`-tier destination refuses `restored`.
  - Every job sets `VCPKG_BINARY_SOURCES` explicitly, starting with `clear;`, so that a runner
    user cache (`~/.cache/vcpkg/archives`) is never consulted implicitly.
  - Publish and verify jobs restore no cache at all; they need no compiler (D3: clean runner).
  - Cache save stays limited to `master` push and `schedule`, and is never done from a tag run.
- Implemented by: 02.0 Task 02 (key scheme, `bootstrap_vcpkg.py` sets `VCPKG_BINARY_SOURCES`);
  03.0 Task 01 (packaging-leg `build` under `tag`); 0012 Story 03.0/04.0 (manifest field, publish
  refusal); P-rule below (R-8).
- Verification: unit test of the planner/stage env: `CI_EVENT=tag` on a packaging leg gives
  `VCPKG_BINARY_SOURCES` beginning `clear` and no `files,...,read` entry. A policy fixture with
  `actions/cache` in a `stage-publish.yml`/`stage-verify.yml` job is rejected. The first
  scratch-tag run (ADR 0005 Validation) shows `cache miss` in RC4 on every packaging leg.

### [HIGH] CR-3 S3 staging destination: the client-side prefix check is the only confinement, and the documented example is bypassable (CWE-22, CWE-284, CWE-668)
- Vector / evidence ([adding-a-publish-destination.md](/docs/dev/adding-a-publish-destination.md),
  illustrative `s3_staging.py`):
  - `prefix.startswith("staging")` accepts `staging-release`, `stagingX` and `staging/../release`.
  - `f['path']` from the manifest is joined unvalidated into both the local source path
    (`{artifact_dir}/{path}`, so `../../` reads any runner file, including a web-identity token
    file) and the S3 key.
  - `CI_RUN_ID` is the same for every re-run attempt of a run, and `aws s3 cp` overwrites
    silently. "A re-run never overwrites another run" therefore holds only across runs, not
    across attempts.
  - No spec states the OIDC trust condition or the role's IAM scope. D9's "refuses a key outside
    `staging/`" lives in code that the A2 actor of CR-1 can change.
- Impact: with a broad role, an overwrite or deletion of release objects in the same bucket, and
  exfiltration of runner files into a readable bucket. With a wildcard trust (`repo:<owner>/*`),
  any repository or branch of the owner can assume the role.
- Mitigation:
  - **Cloud side (the boundary):**
    - Trust policy `StringEquals` on `token.actions.githubusercontent.com:aud = sts.amazonaws.com`
      and `:sub = repo:<owner>/<repo>:environment:staging`. No `StringLike` wildcard.
    - Role policy: allow `s3:PutObject`, `s3:PutObjectTagging` and `s3:GetObject` only on
      `arn:aws:s3:::<bucket>/staging/*`. No `DeleteObject`, ACL or bucket-policy actions.
    - Release locations live in a different bucket, or are covered by an explicit bucket-policy
      `Deny` for the staging role on keys outside `staging/`, with versioning (or Object Lock) on
      the release prefix.
    - Session duration at most 15 minutes. A lifecycle expiry on `staging/`.
  - **Client side (defence in depth):**
    - The prefix must equal `staging` or start with `staging/`, and every component must match
      `^[A-Za-z0-9._-]+$`, with `.`/`..` rejected.
    - The key is built only from validated parts: version `^\d+\.\d+\.\d+(-[0-9A-Za-z.]+)?$`,
      run id and attempt (digits).
    - Files come only from manifest entries whose name matches the D4 basename regex (no
      separator), resolved under `dist/`, regular files only.
    - Writes are conditional (`put-object --if-none-match '*'`), so no attempt overwrites.
    - Never print the role ARN, the bucket policy, a presigned URL or a credential.
  - Fix the illustrative example in the how-to.
- Implemented by: SC5 contract text (this milestone); 0012 Story 04.0 Task 05
  (`s3_staging.py`); the cloud-side setup (maintainer); `docs/dev/adding-a-publish-destination.md`.
- Verification: `test_s3_staging.py` rejects `staging-release`, `staging/../x`, `a/../../b`, a
  manifest path with `/` or `..`, a symlink in `dist/`, and an existing key (stub `aws` returns
  `PreconditionFailed` -> hard failure). A recorded `aws iam simulate-principal-policy` (or a real
  dry run) shows `PutObject` on `release/x` denied and `DeleteObject` on `staging/x` denied.

### [MEDIUM] CR-4 Workflow-command and service-message injection via tool output (T-3, CWE-77, CWE-117, CWE-150)
- Vector / evidence:
  - Done (Story 01.0): every excerpt is fenced. GitHub uses `::stop-commands::<token_hex(16)>`
    (`reporters/github.py:61-69`). TeamCity uses `disableServiceMessages`, plus `_neutralise`
    inside the fence (`reporters/teamcity.py:39-47`). Annotation text is escaped
    (`github.py:20-30`, `teamcity.py:27-36`). `safe_line` strips ESC/C0/C1/bidi characters
    (`ci_step.py:104-120`). Tests: `test_HostileOutputCannotInject`,
    `test_HostileTeamcityLineInEveryBackend`.
  - Gaps:
    1. Lines printed **outside** any fence are not neutralised: `ok:` (with `--summary`),
       `skip:` reasons, `info:` lines, and the RC4 header. GitHub only interprets a command at
       line start, and labels must start alphanumeric (`ci_step.py:102`), so those lines are
       safe there. TeamCity documents one message per line but does not document mid-line
       behaviour, so `ok: x: ##teamcity[...]` must be treated as interpretable.
       `TeamcityReporter.step_ok`/`step_skip` pass the summary through unchanged
       (`teamcity.py:53-55, 72-74`).
    2. Story 02.0/03.0 sibling scripts print child-derived text without `ci_step`'s excerpt path:
       - `print_env.py` prints probed versions;
       - `apt_install.py` prints host names from `/etc/apt/sources*`;
       - `vcpkg_cache_report.py` prints parsed counts;
       - `ctest_report.py` prints JUnit test names in discrepancy lines;
       - `cli_format_check.py` relays the child's `ok: <fmt>, <N> ...` line;
       - `gui_guards.py` prints build-tree paths.
       A crafted SMBIOS table (A4) or a dependency's output reaches these.
    3. The legacy `##[command]` syntax (for example `##[set-output]`, `##[error]`) is not covered
       by the hostile fixture. It is fenced by `stop-commands` today, but unfenced lines must
       not carry it either.
  - Positive: `head_ref`/`ref_name` cannot carry `:` or `[` (git-check-ref-format), so ref names
    cannot inject.
- Impact: forged annotations or a forged `buildStatus` (a red step reported green), early fence
  close on TeamCity, and in a publish job a forged step output (`set-output`) feeding an `if:`.
- Mitigation:
  - Add `Reporter.info(line)` and route **every** printed line of every `scripts/ci/` script
    through `ok_line`/`skip_line`/`info`. Each applies `safe_line`, and the TeamCity backend
    applies `_neutralise` to every line it does not author itself, not only to excerpt lines.
  - Every child-derived token placed outside a fence must match a strict allowlist:
    - versions `^[0-9A-Za-z.+_-]{1,40}$`, else `?`;
    - host names `^[A-Za-z0-9.-]{1,253}$`, else `<invalid>`;
    - test names `^[A-Za-z0-9_./:-]{1,120}$`, else `<test #n>`;
    - counts as integers only.
  - `cli_format_check.py` parses the child's count with an anchored regex and re-renders the
    line; it never relays it.
  - P11 extends to forbid `print(`/`sys.stdout.write` in `scripts/ci/*.py` outside `ci_step.py`
    and `reporters/`, so the "single emitter" rule is mechanical.
- Implemented by: 01.0 follow-up (reporters, `info`); 02.0 Tasks 01-03 (`print_env.py`,
  `apt_install.py`, P11); 03.0 Tasks 01-03 (`cli_format_check.py`, `ctest_report.py`,
  `gui_guards.py`).
- Verification:
  - `hostile.log` gains `##[set-output name=x;]y`, `##[error]x` and a line containing
    `ok: x ##teamcity[buildStatus text='green']`.
  - For every backend, `step_ok`/`step_skip`/`info` given a hostile summary print no
    `##teamcity[` that the backend did not author.
  - Each sibling script's test feeds `::error::` and `##teamcity[` through every child-derived
    field (version, host, test name, CLI line) and asserts that neither appears at line start
    and that `##teamcity[` appears nowhere.

### [MEDIUM] CR-5 Child processes inherit platform side channels and publish credentials (CWE-15, CWE-214, CWE-522)
- Vector / evidence: `reporters/__init__.py:63-74` `child_environment()` removes only the three
  debug switches. Every child (cmake, the compiler, vcpkg port scripts, ctest, test binaries, and
  later `tar`/`aws`) inherits:
  - `GITHUB_ENV`/`GITHUB_PATH`/`GITHUB_OUTPUT`/`GITHUB_STATE`/`GITHUB_STEP_SUMMARY`. A child can
    set `LD_PRELOAD`/`BASH_ENV`/`PATH`, a step output or the summary for **later steps of the same
    job**, bypassing every fence.
  - In publish jobs, `ACTIONS_ID_TOKEN_REQUEST_TOKEN`/`_URL` (mint an OIDC token, then assume the
    role), `CI_PUBLISH_TOKEN`, and `AWS_*` session variables.
  - `actions/checkout` defaults to `persist-credentials: true`. That writes the job's
    `GITHUB_TOKEN` into `.git/config`, where every later step can read it, and where a workspace
    artifact would publish it (the "ArtiPACKED" class, 2024). No spec sets it to false.
- Impact: in build jobs, A3 code gains persistence across steps (self-harm for A1). In a publish
  job, any helper binary gains the write credential.
- Mitigation:
  - `child_environment()` also drops every `GITHUB_*` file-command variable,
    `ACTIONS_ID_TOKEN_REQUEST_*`, `ACTIONS_RUNTIME_TOKEN`, `ACTIONS_CACHE_URL`,
    `ACTIONS_RESULTS_URL`, `CI_PUBLISH_*`, `AWS_*` and `TEAMCITY_*`/`BUILD_*` password
    parameters.
  - A step that genuinely needs one passes it by name, for example
    `run_step(..., pass_env=("AWS_WEB_IDENTITY_TOKEN_FILE",))`. A destination exchanges the OIDC
    token itself, writes it to a 0600 file under `CI_TEMP_DIR` and passes only that file's path
    to `aws`.
  - New policy rule (P14, or folded into P2): every `actions/checkout` has
    `persist-credentials: false`.
- Implemented by: 01.0 follow-up (`child_environment`); 02.0 Task 03 (P14); 0012 Story 04.0
  (destination credential hand-off).
- Verification: `test_ChildDoesNotInheritDebugSwitches` is extended to cover every name above,
  plus a positive `pass_env` case. A policy fixture with a checkout lacking
  `persist-credentials: false` is rejected.

### [MEDIUM] CR-6 Expression injection and untrusted context values (CWE-94, CWE-77, CWE-93)
- Vector / evidence:
  - P6 bans `${{ }}` in `run:` and P7 makes `run:` one `stage.py` line, so the classic
    `run: echo "${{ github.event.pull_request.title }}"` is impossible.
  - Remaining paths:
    1. P10 restricts `env:` **keys** but not which **contexts** feed them. A
       `CI_X: ${{ github.event.pull_request.title }}` or a commit-message mapping is permitted,
       and scripts could pass it to a tool argv or print it.
    2. `workflow_dispatch` inputs (04.0 Task 02: `jobs`, `os`) reach `plan.py`. A2 can send any
       string through the API even for `type: choice` inputs on another ref's YAML.
    3. `plan.py` writes the matrix to the job-output file. A value containing a newline, or the
       heredoc delimiter, forges extra outputs (CWE-93).
    4. `runs-on: ${{ matrix.label }}` from `fromJSON(plan output)` escapes P3, which checks only
       literal labels.
    5. Actions that evaluate code from inputs (`actions/github-script`) or composite/local
       actions whose `run:` P6/P7 do not scan.
- Impact: shell or argument injection inside a CI job, a forged plan (legs or publish rows
  selected), or a job on an unintended runner label.
- Mitigation:
  - [OVERRIDES SPEC] P10 allows only these contexts on the right-hand side of `env:`:
    - `github.{run_id,run_attempt,server_url,repository,event_name,ref,ref_name,ref_type,sha,workspace}`;
    - `github.event.before` and `github.event.pull_request.base.sha`;
    - `runner.temp`, `matrix.*`, `needs.plan.outputs.*`, and `inputs.*` of the declared choice
      inputs.
    - `head_ref`, any `*.title`, `*.body`, `*.message`, `*.head_commit.*`, `*.label*` and
      `*.name` of PR/issue/comment objects are violations.
  - `plan.py`/`stage.py` re-validate every input against their allowlists (an unknown value is
    exit 2) and never trust the platform's choice validation.
  - The reporter writes job outputs only as single-line JSON with no CR/LF, using a random
    delimiter. That gives the neutral output channel a name in `env_names.py`.
  - `plan.py` emits only labels found in the pins data file, and P3 checks the pins file itself.
  - P13 rejects `actions/github-script` and any `uses: ./...` local or composite action. Composite
    third-party actions are rejected unless their transitive `uses:` are themselves SHA-pinned
    (none are needed today).
- Implemented by: 02.0 Task 03 (P3, P6, P10 [OVERRIDES SPEC], P13); 03.0 Task 01 (`stage.py`
  input validation); 04.0 Task 02 (`plan.py`, output channel).
- Verification:
  - Policy fixtures: `CI_T: ${{ github.event.pull_request.title }}` and `github.head_ref` mapped
    -> violation; `uses: actions/github-script@<sha>` -> violation.
  - `plan.py` tests: input `all\nmatrix=...` -> exit 2; output values never contain CR/LF; an
    unknown label in `legs.json` -> exit 2.

### [MEDIUM] CR-7 Third-party action and tool supply chain (CWE-829, CWE-494, CWE-1357)
- Vector / evidence:
  - P2 (40-hex SHA plus a version comment) and P13 (an allowlist with justification) are the
    right controls. The March 2025 `tj-actions/changed-files` tag-repointing compromise
    (CVE-2025-30066, a CISA KEV entry, secrets dumped into logs) is the precedent they defend
    against.
  - Gaps:
    1. A SHA can be an "impostor commit" from a fork network, which GitHub serves under the
       parent repository's name. Nothing checks that the pinned SHA is the upstream tag's commit.
    2. `docker://` uses and an action's own floating dependencies are not addressed.
    3. `lukka/run-vcpkg` is still named in 02.0 Task 01 ("Set `run-vcpkg`'s
       `vcpkgGitCommitId`") and in 03.0 Task 01's `build` step list, although 02.0 README
       (ADR 0005 reversal) replaces it. 02.0 Task 02's Files list does not include
       `bootstrap_vcpkg.py`, so no spec says how it is pinned or verified.
    4. `requirements-tools.txt` uses `--require-hashes --no-deps` but not
       `--only-binary :all:`. A missing wheel for one platform then falls back to an sdist
       build, which executes code.
    5. `install_actionlint.py` checks a SHA-256 (good) but unpacks a tarball. Python 3.9-3.11's

### [MEDIUM] CR-8 Artifact tampering between build, package, verify and publish (CWE-345, CWE-354, CWE-22)
- Vector / evidence:
  - D4 has `verify`/`publish` refuse any digest that differs from `manifest.json`. But the
    manifest travels in the same artifact store as the archives. Any job of the same run that
    holds the runtime token can delete and re-upload an artifact of the same name, and that
    includes a build/test leg executing A3 code. Replacing both the archive and the manifest
    passes the check.
  - The manifest's `file` names and the `install/<leg>/` tree are consumed as paths.
  - SC2's `install/` hand-off (this milestone) has no digest at all.
- Impact: shipped bytes differ from tested bytes (DD1 broken), or a path traversal during
  extraction in `verify`/`publish`.
- Mitigation:
  - The `build` stage on a packaging leg computes a tree digest of `install/<leg>/` (sorted
    relative paths plus file SHA-256, no symlinks allowed) and exports it as a **job output**.
  - `package` checks that digest before archiving and exports the `manifest.json` SHA-256 and
    the uploaded artifact IDs as job outputs.
  - `verify` and `publish` download by artifact ID, check the manifest digest against
    `needs.package.outputs`, then check each file against the manifest. Job outputs are written
    only by the job that owns them, so a sibling job cannot forge them.
  - `publish` re-checks itself and never relies on `verify`'s verdict alone.
  - Manifest `file` entries must match
    `^libbios-<version>-<leg>\.(tar\.gz|zip)(\.sha256)?$` with no separator.
  - Archive creation rejects symlinks, absolute paths and `..`. Extraction in `verify` uses the
    same member checks as CR-7.
- Implemented by: SC2 (03.0 Task 01: tree digest output for `install/`); 0012 Story 03.0
  (package, manifest) and Story 04.0 (verify/publish).
- Verification: tests for the tree digest (a file added, changed or symlinked -> mismatch) and
  for the manifest name regex; the ADR 0005 Validation "corrupted archive fails verify" proof,
  plus a second proof that replaces the archive **and** the manifest and fails on the job-output
  digest.
